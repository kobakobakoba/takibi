# 調査メモ 2026-10-12：文字以外（スタンプ・画像など）が届いたときのひとこと ― 実装方法を決める材料

調査部。テーマは社長の指定（バックログ候補「文字以外（スタンプなど）が届いたときのひとこと」）。
(1) line-bot-sdk v3 の `WebhookHandler` で、新しい import なしにテキスト以外を受けられるか（`@handler.add(MessageEvent)` と `@handler.default()` の挙動）。
(2) スタンプだけ・画像だけを送る人に、どんな一言が安心につながるか。
(3) 画像・音声を受けても、中身を取得しなければ焚き火のサーバーに何も残らない、という理解で正しいか。

※ 今日も **`linebot/v3/webhook.py` の本体は読めなかった**（GitHub の blob、raw.githubusercontent.com、jsDelivr、readthedocs の v3 ページはすべて取得の許可待ちが切れた。GitHub の v3 ファイルは2回試した）。読めたのは、**旧版（v1系）の `linebot/webhook.py`**（GitHub master と readthedocs）、PyPI の最新版ページの README、GitHub のリリース一覧、v3 のサンプル `app_with_handler.py`、LINE の Messaging API リファレンス（日本語 nojs 版）、厚労省の SNS 相談ガイドライン（PDF）、gunicorn の設定ドキュメントなど。

## 1. `WebhookHandler` でテキスト以外を受ける方法

### 1-1. 確認できたこと（事実）

**(A) 旧版 `linebot/webhook.py`（v1 系の `WebhookHandler`、master にまだ残っている）のソース**

GitHub master と readthedocs の両方で、同じ作りを確認した。

- `add(event, message=None)` は、`__get_handler_key` で作ったキーで `self._handlers` に関数を登録する。キーは、`message` がなければイベントのクラス名だけ（例 `MessageEvent`）、あれば「イベント名_メッセージ名」（例 `MessageEvent_TextMessage`）。**キーが別なので、2つの登録は上書きし合わない。**
- `default()` は関数を `self._default` に入れるだけ。
- `handle()` はイベントごとに、次の順で1つだけ選んで呼ぶ：
  1. `MessageEvent` なら「イベント名_メッセージ名」のキーで探す
  2. 見つからなければ「イベント名」だけのキーで探す
  3. それでもなければ `self._default`
  4. それもなければ、ログにキー名だけを info で出して何もしない（ソースの該当行：`'No handler of ' + key + ' and no default handler'`）。
- このファイルの `WebhookHandler` には、3.0.0 で非推奨・`linebot.v3.webhook` を使うよう案内する `@deprecated` が付いている（GitHub ページの要約で確認）。

**(B) PyPI 最新版（3.26.0）のページの README**

- `default` の説明：「If there is no handler for an event, this default handler method is called.」（イベントに対応するハンドラがないときに呼ばれる）。
- `message=` を省いたときの選ばれ方は、README には書かれていない。

**(C) v3 での使い方の例**

- 公式サンプル `examples/flask-echo/app_with_handler.py` は `from linebot.v3 import WebhookHandler` と `@handler.add(MessageEvent, message=TextMessageContent)` を使い、`default` は使っていない。
- v3.25.0 のリリースノート（Message Edited Webhook）は、`MessageEvent` ではない `MessageEditedEvent` に `message=TextMessageContent` を付けて登録する例を載せている。

### 1-2. 推測（v3 本体を読めていないので、ここからは推測）

- **(a) `@handler.add(MessageEvent)`（message= なし）と `@handler.add(MessageEvent, message=TextMessageContent)` の併用**：v3 も旧版と同じ「メッセージ種別つきのキー → イベントだけのキー → default」の順なら、**テキストは今までどおり `on_message`、スタンプ・画像・音声などは message= なしの方**に届く。旧版のこの順番は確認済みだが、v3 で同じかは**未確認**。
  - v3.25.0 で `MessageEvent` 以外にも `message=` を付ける例があるので、v3 の `handle()` は「MessageEvent かどうか」ではなく別の条件（例：`message` 属性があるか）で見分けている可能性がある（推測）。どちらでも、`MessageEvent` に対する順番は変わらないと思われる（推測）。
- **(b) `@handler.default()`**：旧版の作りなら、**登録のないイベントすべて**で呼ばれる。焚き火は `FollowEvent`、`UnsendEvent`、`MessageEvent`＋`TextMessageContent` を登録しているので、この3つでは default は呼ばれない。一方で、**スタンプ・画像などのほかに、ブロック（unfollow）、ポストバック、グループ参加・退出、`MessageEditedEvent`（グループのみ）、今後 LINE が足す新しいイベント**などでも呼ばれる（推測。旧版の順番と、焚き火の登録状況からの読み）。
  - ブロックや送信取消には reply token がない（送信取消に reply token がないことは `main.py` のコメントでも前提にしている）。default で一律に返信すると、返せないイベントで `reply()` が失敗する。`reply()` は例外を外に出さないので落ちはしないが、`reply failed` の行が増える（コードを読んでの推測）。
  - **default より `@handler.add(MessageEvent)`（message= なし）の方が、届く範囲が「メッセージ」だけに絞られて安全**（推測）。

### 1-3. 開発部への材料（推測を含む提案）

- **新しい import は要らない**：`MessageEvent` と `TextMessageContent` はすでに import 済み（`main.py` 26行目）。`@handler.add(MessageEvent)` で受ければ、`StickerMessageContent` などを足さずに済む。10-06 からの「SDK への新しい依存を重ねない」方針に当たらない。
- **優先順位が未確認でも安全にする書き方**：message= なしの関数の最初で `isinstance(event.message, TextMessageContent)` を見て、テキストなら `on_message(event)` に渡して終わる。こうしておけば、仮に v3 の順番が違って テキストがこちらに来ても、今までどおりの動きになる（推測。1つのイベントで呼ばれる関数は1つだけ、という旧版の作りが前提）。
- **テストの注意（コードを読んで確認）**：`tests/test_main.py` のダミー `WebhookHandler.add()` は `message` を無視し、イベントのクラス名だけをキーにしている。`@handler.add(MessageEvent)` を足すと、ダミーの中では `on_message` の登録が上書きされる。既存のテストは `main.on_message` を直接呼んでいるので壊れないと思われるが、振り分けを確かめるテストを書くなら、ダミーのキーを「イベント名_メッセージ名」に直す必要がある。なお、ダミーは本物の SDK ではないので、テストで確かめられるのは「登録したこと」までで、v3 本体の優先順位は確かめられない。
- **本番での確かめ方（オーナー向けの候補）**：反映後、スタンプを1つ送ってひとことが返ること、続けて文字を送って普段の返事が返ることを見れば、優先順位の問題がないと分かる。

## 2. スタンプだけ・画像だけを送る人への一言

### 2-1. 確認できたこと

- **LINE の仕様（スタンプ）**：スタンプのイベントには `packageId`、`stickerId`、`stickerResourceType`、`keywords`（スタンプを表すキーワード、最大15個。試験的な提供）、`text`（**メッセージスタンプのときだけ、利用者が入れた文字。最大100文字**）が付く（Messaging API リファレンス 日本語）。つまり、**スタンプでも利用者の言葉が届く場合がある**。
- **支援現場の指針（厚労省「自殺対策における SNS 相談事業 ガイドライン」）**：
  - 「何から話していいのか分からない」「うまく話せない」相談者には、ゆっくりでよいこと、思い浮かぶことを少しずつ言葉にすればよいことを伝える応答例がある（p.28）。
  - 突然送られてきた動画やリンクは、基本的に開かない（p.21）。
  - 相談員の側がスタンプ・絵文字を使うのは、受け取り方が人によって違うため控えめに、という趣旨（p.14）。
  - 相談の現場では記録を残す（p.26、p.14 に「相談内容が記録として残ります」）。**焚き火は残さないので、ここは現場と違う**。
  - 読んだのは厚労省サイトにある改訂前の版。2026年3月付の「令和7年度改訂版」が出ている（三菱UFJリサーチ＆コンサルティングのサイトに PDF）が、今日は中身を読んでいない。
- **競合・他の相談窓口**：千葉県・神奈川県・仙台（ワンファミリー仙台）の LINE 相談の案内ページ、LINE 公式アカウントの AI チャットボット（β）のヘルプには、スタンプや画像を受けたときの扱いの記載はなかった。千葉県のページは「ほんの少しでも思い悩んでいること」でよいと案内している。**スタンプ・画像への返し方の具体例は、今日は見つからなかった。**

### 2-2. 一言の案（推測。上の材料からの組み立て）

伝えたいことは4つ：(1) 届いたことを受け止める、(2) 文字にしなくても責めない、(3) 焚き火は中身を開かない・残さない、(4) 言葉にできるときに、ひとことでいい。

- 案 S-A（短い）：
  「受け取りました🔥 焚き火は文字にだけ返事をします。スタンプや画像は開かず、残しません。言葉にできそうなときに、ひとことだけでも大丈夫です。」
- 案 S-B（もっとやわらかく）：
  「届いてるよ。うまく言葉にならない日もあるよね。焚き火は文字にだけ返事をしていて、スタンプや画像の中身は開かないし、残さないよ。ひとことでも、まとまってなくても、そのまま送ってね。」

守ること（推測を含む）：
- 「文字で送ってください」「対応していません」のような断る言い方や命令形にしない（約束4「責めない」に近づける）。
- **「残しません」の範囲は焚き火のサーバーだけ**。LINE のトーク画面には残り、画像などは LINE のサーバーにも一定期間ある（3-1）。10-11 の文言のルールどおり「どこにも残らない」「完全に消える」とは書かない。必要なら「LINE のトーク画面には残ります」は「使い方」に任せる。
- AI（Claude）には渡さない固定文にする（Claude の料金がかからず、スタンプのキーワードなども外に出ない）。
- 何度スタンプが来ても同じ文でよい。「前にも返した」を覚えるには記録が要るので、作らない。
- **安全面の論点（安全審査部に回したい）**：メッセージスタンプの `text` には、利用者の言葉（例えば「しにたい」）が入りうる。固定文だけを返すと、その場で相談先が出ない。`text` を読んで `SAFETY_USER_WORDS` に当たるときだけ 110番・119番の一文を添えるか、そもそも `text` を読まないかは、安全審査部の判断が要る（推測。メッセージスタンプがどれくらい使われるかは未確認）。

## 3. 中身を取得しなければ、焚き火のサーバーに何も残らないか

### 3-1. 確認できたこと

- **Webhook に画像・音声のデータそのものは入っていない**。画像・動画・音声・ファイルのイベントには `id` や `contentProvider` などの情報だけが入り、データは「コンテンツを取得する」API にメッセージ ID を渡して別に取りに行く（`contentProvider.type` が `line` の場合）（Messaging API リファレンス 日本語）。
- 同じリファレンスは、利用者が送ったコンテンツは**一定期間で自動的に削除され、保存期間は保証されない**としている。つまり **LINE のサーバーには、焚き火が取りに行かなくても一定期間ある**（期間は非公開）。
- 取得には `MessagingApiBlob` の `get_message_content` を使う（第三者の解説記事。`main.py` はこれを import も呼び出しもしていないことは grep で確認）。
- gunicorn の設定：アクセスログ（`accesslog`）は初期値 `None`（書かない）。アクセスログの書式の項目にリクエストの本文はない。エラーログの初期値は標準エラー出力（gunicorn 21.0.1 のドキュメント）。焚き火の起動コマンドは `gunicorn main:app --workers 1 --threads 4` でログの指定はない（README で確認）。

### 3-2. 結論（確認済みのことと推測を分ける）

- **おおむね正しい。** 焚き火が `get_message_content` を呼ばなければ、画像・音声のデータは焚き火のサーバーに届かない（確認済み：Webhook にデータが入っていない）。
- ただし「何も届かない」わけではない。Webhook の本文には、メッセージ ID、スタンプの ID・キーワード・メッセージスタンプの文字、**ファイルならファイル名**、位置情報なら住所や緯度経度などが入る（スタンプはリファレンスで確認。ファイル名・位置情報の項目は今日のリファレンスの要約では確認しきれていないので**未確認**）。これらは処理の間メモリにあるだけで、焚き火のコードはファイルにもログにも書かない（コードを読んでの確認。ハンドラで `sessions` に入れない限り）。
- **残る可能性のある所（推測）**：
  - 未処理の例外が出ると、Flask／gunicorn がエラーの詳細をエラーログに出す（10-09 の推測と同じ）。ハンドラの中は小さく、例外を出しにくい書き方にする。
  - v3 の `handle()` が、ハンドラがないときにキー名を info ログに出すか（旧版はキー名だけを出す）。キー名はクラス名なので中身は入らない（旧版で確認。v3 は未確認）。
  - Render 側が HTTP リクエストを記録しているか、その記録に本文が入るかは**未確認**（会社から見えない）。
- **焚き火の外には残る**：LINE のトーク画面、LINE のサーバー（コンテンツは一定期間）。これは「使い方」の【残るもの】の書き方と矛盾しない。

## 会社への示唆（3つ以内）

1. **新しい import なしで作れる見込みが高い（推測）。** `@handler.default()` ではなく `@handler.add(MessageEvent)`（message= なし）で受け、関数の最初で「テキストなら `on_message` に渡す」守りを入れれば、v3 の優先順位が未確認でも今の動きを崩さない。default はブロック・ポストバック・将来のイベントまで拾うので使わない。旧版のソースでは「種別つき → イベントだけ → default」の順を確認済み。v3 本体は今日も読めていないので、反映後にオーナーにスタンプ1つと文字1つで確かめてもらうとよい。
2. **一言は固定文で、AI に渡さず、「焚き火は開かない・残さない」までを言う。** 断る・命令する言い方を避け、「ひとことでも、まとまってなくても」で受け止める（案 S-A／S-B）。「残さない」は焚き火のサーバーに限る（LINE のサーバーには画像が一定期間ある）。
3. **メッセージスタンプには利用者の文字（最大100文字）が入る。** 「しにたい」などが入っていても、固定文だけでは相談先が出ない。読むか読まないか、読むなら 110番・119番の一文を添えるかを、作る前に安全審査部に判断してもらう。
