# 調査メモ 2026-10-23：line-bot-sdk v3 の振り分け順（スタンプのひとこと・返信失敗時の文脈が止まっている件）

調査部。テーマは社長の推奨1。line-bot-sdk（Python, v3）の `WebhookHandler` が、テキスト以外のメッセージ・`message=` なしの登録・`default` をどの順で選ぶかを公式資料で確かめ、`main.py` の今のハンドラと照らし合わせる。コードは変更していない。

**結論を先に：v3 本体（`linebot/v3/webhook.py`）は今日も読めなかった（5回目）。振り分け順は未確認のまま。** ただし、順番が分からないままでも進められる作り方の比較と、順番を確実に確かめる方法（オーナー作業）を整理した。

## 1. 今日確かめられたこと（事実）

### 1-1. SDK の版

- PyPI の最新版は **3.26.0（2026年9月29日公開）**、必要な Python は **3.10 以上**（PyPI 最新版ページ）。
- `requirements.txt` の下限 3.11.0 は 2024年4月17日公開で、当時の必要 Python は 3.8 以上（PyPI 3.11.0 ページ）。
- `requirements.txt` は `line-bot-sdk>=3.11` で上限がないので、本番を作り直すたびに、その時点の最新（今なら 3.26.0）が入りうる（推測。Render のビルドの様子は会社から見えない）。本番の版はオーナーの確認待ちのまま。

### 1-2. 公式 README（PyPI 3.26.0／GitHub）に書いてあること

- `default` の説明：「If there is no handler for an event, this default handler method is called.」（PyPI 最新版ページの README）。
- `add` は「イベントとメッセージの種類を指定して登録する」説明だけ。**`message=` を付けた登録と付けない登録が両方あるとき、どちらが選ばれるかは書かれていない**（PyPI・GitHub の README とも）。
- README の例は `linebot.v3` から import しているが、`add` の説明文には旧版の `TextMessage` という名前が残っている（GitHub README）。説明文が v3 用に書き直されていない箇所がある、ということ。

### 1-3. 旧版（v1系）`linebot/webhook.py` のソース（readthedocs）

10-12 の確認と同じ内容を今日も確かめた。`handle()` はイベントごとに「`MessageEvent` ならイベント名＋メッセージ名のキー → イベント名だけのキー → `default` → どれもなければキー名だけを info ログ」の順で **1つだけ** 選んで呼ぶ。このクラスには 3.0.0 で非推奨・`linebot.v3.webhook` を使う旨の注記がある。**v3 が同じ作りかは、これでは分からない。**

### 1-4. v3 のメッセージ種類のクラス

- 第三者のまとめ（tessl.io の SDK 解説）では、v3 の webhooks に `TextMessageContent`、`ImageMessageContent`、`StickerMessageContent` などがあり、`StickerMessageContent` は `package_id`、`sticker_id`、`sticker_resource_type`、`keywords`、`text`（任意）を持つ、と書かれている。`@handler.add(MessageEvent, message=ImageMessageContent)` の形の例もある。公式ソースではないので「名前はほぼ確か、3.11 時点での有無は未確認」として扱う。
- 公式サンプル `app_with_handler.py`（v3）は `@handler.add(MessageEvent, message=TextMessageContent)` の1つだけで、`default` も `message=` なしの登録も使っていない。

## 2. `main.py` の今のハンドラ（コードを読んで確認）

- 登録は3つ：`@handler.add(FollowEvent)`（228行）、`@handler.add(UnsendEvent)`（233行）、`@handler.add(MessageEvent, message=TextMessageContent)`（242行）。`default` も `message=` なしの `MessageEvent` もない。
- import は `FollowEvent, MessageEvent, TextMessageContent, UnsendEvent`（27行）。
- 今は、スタンプ・画像などが届いても対応する登録がなく、何も返さない（旧版と同じ作りなら info ログにキー名だけが出る。推測）。
- テストの偽 `WebhookHandler.add()`（`tests/test_main.py` 41〜45行）は `message` を無視し、イベントのクラス名だけで登録する。`MessageEvent` を2回登録すると後の方で上書きされる。偽物なので v3 の順番はテストでは確かめられない（10-12 と同じ）。

## 3. 作り方の比較（ここから推測。v3 本体を読めていないため）

スタンプのひとことを作る方法は3つある。**どれも v3 の順番を読めないまま作ることになる**ので、壊れ方を比べる。

| 案 | 登録の形 | 順番への依存 | v3 が想定と違ったときの壊れ方（推測） |
| --- | --- | --- | --- |
| (A) 10-12 の決定 | 既存のテキスト用はそのまま＋`@handler.add(MessageEvent)`（message= なし）。関数の頭で `TextMessageContent` なら `on_message` に渡す | 「1つのイベントで呼ばれる関数は1つだけ」に依存 | もし v3 が両方呼ぶ作りなら、テキストで `on_message` が2回動き、Claude を2回呼ぶ・同じ発言が履歴に2つ入る・2回目の返信は失敗する。もし v3 が message= なしを優先する作りでも、守りがあるのでテキストは今どおり |
| (B) 新案 | 既存のテキスト用はそのまま＋`@handler.add(MessageEvent, message=StickerMessageContent)` | テキストと同じ「種類つきのキー」だけを使う。種類つきとイベントだけの優先順の問題が**そもそも起きない** | `StickerMessageContent` が本番の版に無いと、**起動時に import で落ち、ボット全体が止まる**。画像・音声などは今までどおり無言（スタンプだけが対象） |
| (C) `default` | `@handler.default()` | 「登録がないときだけ呼ぶ」は README で確認済み | ブロック・ポストバック・将来のイベントまで拾い、返信できないイベントで `reply()` が失敗する（10-12 の指摘のまま）。勧めない |

- (A) の「両方呼ぶ」は、README の `default` の説明（登録がないときに呼ぶ）や旧版の作り（辞書から1つ選ぶ）から見て、起きにくいと考える（推測）。
- (B) は順番の問題を避けられる代わりに、10-09 から避けてきた「SDK への新しい依存」に当たる。`StickerMessageContent` は v3 のモデル群（OpenAPI から自動生成）の基本の種類なので 3.11 にもある可能性が高い（推測）が、確かめていない。
- どちらの案でも、作った日に**オーナーがスタンプ1つと文字1つを送って確かめる**のは必要（10-12 と同じ）。

## 4. 順番を確実に確かめる方法（オーナーにしかできない）

会社からは本番の環境もソースも見えない。オーナーが、本番と同じ版の line-bot-sdk が入った環境（手元の PC で `pip install "line-bot-sdk==本番の版"` でも可）で、次の1行を実行して結果を貼ってもらえれば、v3 の `handle()` の中身がそのまま分かる（会話や秘密の値は含まれない）。

```
python -c "import inspect, linebot.v3.webhook as w; print(inspect.getsource(w.WebhookHandler))"
```

あわせて `python -c "import linebot.v3.webhooks as m; print(hasattr(m, 'StickerMessageContent'))"` で (B) の import の有無も分かる。どちらも、すでに頼んでいる「line-bot-sdk と Python の版番号の確認」と同じ機会にお願いできる。

## 5. 「返信失敗時の文脈」との関係（バックログを読んで確認）

- バックログの「返信失敗時、安全フラグが立った発言は文脈に残すか」（2026-10-09 の申し送り）は、`answer_and_reply()` の中（325〜328行）の扱いの話で、**SDK の振り分け順には依存しない**。止まっている理由は安全審査部との検討待ち。v3 の確認を待たずに、企画部→安全審査部の事前相談に回せる。

## 確認できなかったこと

1. v3 の `WebhookHandler.handle()` の振り分け順（種類つき／イベントだけ／default）と、1つのイベントで呼ばれる関数が1つだけかどうか。
2. `StickerMessageContent` が 3.11.0 にあるか（クラス名は第三者のまとめで確認、公式ソースでは未確認）。
3. 本番に入っている line-bot-sdk と Python の版。
4. v3 の `add()` が `message=[A, B]` のように複数の種類をまとめて受けるか（旧版は受ける）。

## 会社への示唆（3つ以内）

1. **v3 の振り分け順は、ネットで公式ソースを読む方法では5回試して確かめられなかった。これ以上調査部で粘るより、オーナーに4の1行を実行してもらうのが確実で早い**（版番号の確認と同じお願いにまとめられる）。結果が来るまで、スタンプのひとことは本番に出さないほうがよい。
2. **作り方は (A)（message= なし＋テキストなら `on_message` に渡す守り）と (B)（`message=StickerMessageContent`）で壊れ方が違う。** (A) は v3 が「両方呼ぶ」作りのときだけ二重処理、(B) はクラスが無いと起動できない。オーナーの実行結果で、どちらの心配が消えるかを見てから選ぶ（推測を含む）。
3. **「返信失敗時の文脈」は SDK の順番と関係ない。** v3 待ちの候補から外し、安全審査部への事前相談に回せば、PERSONA 以外の改善として前に進められる。
