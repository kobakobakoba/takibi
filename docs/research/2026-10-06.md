# 調査メモ 2026-10-06：送信取消イベントの仕様と、SAFETYで案内している相談窓口の確認

調査部。テーマは社長の提案どおり2つ。
(1) バックログ候補1「送信取消イベントで会話を消す」を実装するための LINE Messaging API と line-bot-sdk（Python v3）の仕様。
(2) `main.py` の SAFETY ブロックで案内している相談窓口が今も有効か。

※ LINE Developers のリファレンス本文（`/reference/messaging-api/`）は今日取得できなかった。代わりに、LINE公式の OpenAPI 定義（line-openapi）と公式SDKのソース、LINE Developers のドキュメント（受信の解説ページ）で確かめた。

## 1. 送信取消イベント（unsend）

### 1-1. いつ・どのトークで届くか（確認済み）

- 利用者が送ったメッセージを「送信取消」したときに届く。取消は送信後の限られた時間内だけできる（具体的な時間は今日は公式で確認できなかった）。
- **1対1トーク・グループ・複数人トークのすべてで届く。** 焚き火は1対1なので対象になる。
- LINE Developers は、取消イベントを受けたら利用者の意図を尊重し、保存しているメッセージを削除するなどして、以後見られたり使われたりしないようにすることを推奨している。
- イベント一覧の表では、メッセージイベントには「返信できる」と書かれているのに対し、送信取消イベントの行にはその記載がない。

### 1-2. イベントの中身（確認済み）

OpenAPI定義（`webhook.yml`）とSDKの `UnsendEvent` クラスで一致を確認した。

| 項目 | 内容 |
| --- | --- |
| `type` | `"unsend"` |
| `source` | 送信元。1対1なら `UserSource`（`userId` を持つ） |
| `timestamp`, `mode`, `webhookEventId`, `deliveryContext` | 全イベント共通の項目 |
| `unsend.messageId` | 取り消されたメッセージのID（必須の文字列） |
| `replyToken` | **ない。** `UnsendEvent` の定義に含まれない |

- **返事は送れない**（返信用トークンがないため）。プッシュメッセージなら送れるが、通数課金の対象になりうるうえ、取り消した直後に話しかけるのは利用者の意図に反しうる（推測）。バックログどおり「何も返さない」でよい。
- SDKの `UserSource.user_id` は `Optional`（`None` になりうる型）。1対1で実際に欠けるケースは今日確認できなかったが、実装では `None` のときは何もしないようにしておくのが安全。
- `messageId` はあるが、焚き火はメッセージIDを保存していないので、取り消された1通だけを消すことはできない。**その人の会話をまるごと消す（燃やすと同じ `sessions.pop`）** のが今の実装に合う。メッセージIDを持つように変えるのは、保存する情報を増やすことになるので勧めない（会社の判断）。

### 1-3. line-bot-sdk（Python v3）での書き方（確認済み）

- クラス名：`UnsendEvent`（中身は `UnsendDetail`、属性名 `message_id`）。どちらも `linebot.v3.webhooks` から import できる。
- `requirements.txt` は `line-bot-sdk>=3.11`。`UnsendEvent` は v3 の webhooks モデルに含まれている（今日見たのは master ブランチ。3.11 時点での有無は、SDKのv3がこのモデル群で始まっていることから問題ないと考えるが、厳密には未確認）。
- ハンドラ登録は既存の `FollowEvent` と同じ形：

```python
from linebot.v3.webhooks import UnsendEvent

@handler.add(UnsendEvent)
def on_unsend(event):
    ...  # event.source.user_id で sessions.pop(user_id, None)。reply は呼ばない
```

- `WebhookHandler.add(event, message=None)`。`message` 引数は `MessageEvent` 用なので、取消では使わない。
- 参考：今の `main.py` は `UnsendEvent` のハンドラを持たないので、SDKは「ハンドラがない」旨をログに出して何もしない（ログに出るのはイベントの種類名で、会話の内容ではない。SDKの `webhook.py` で確認）。

### 1-4. 実装時の注意（開発部・安全審査部向け）

- **テストのダミー**：`tests/test_main.py` の偽 `linebot.v3.webhooks` に `UnsendEvent` を足す必要がある（今は `FollowEvent`, `MessageEvent`, `TextMessageContent` の3つだけ）。偽の `WebhookHandler.add` はクラス名で登録しているので、`handlers["UnsendEvent"]` で呼べる。
- **返事待ち中の取消**：Claudeの返事を待っている間に取消が来て `sessions.pop` されると、`on_message` の後半の `sessions[user_id]["updated"]` で KeyError になりうる（コードを読んでの指摘。候補4で既に挙がっている「燃やす」と同じ問題で、消す経路が1つ増える）。
- **会話がない人の取消**：`sessions.pop(user_id, None)` なら何も起きない。燃やしたあとの取消も同じ。

### 1-5. 関連：メッセージ編集イベント（新しく分かったこと）

- LINEは2026年8月に、送信後15分以内のメッセージ編集機能を発表した（LINEラボで試用、秋以降はLYPプレミアム会員向け、と報道）。
- Messaging API には編集イベント（`MessageEditedEvent`、返信用トークンあり）があり、SDKにもクラスがある。
- ただし LINE Developers の表では、**編集イベントが届くのはグループトークだけで、1対1トークには届かない。** つまり焚き火では、利用者がメッセージを編集しても、ボットのメモリには編集前の文が残る。
- 今すぐの実装は不要（1対1では受け取れないため）。「使い方」の説明に編集のことを書く必要があるかは企画部の判断（今の `HELP_TEXT` は編集に触れていないので、食い違いはない）。

### 結論

**「要修正」（間違った窓口・使えなくなった窓口）は見つからなかった。**

ただし、次の2点は「間違いではないが、案内が実態とずれうる」ので、オーナーへの**提案**として記録する（SAFETYブロックの変更はオーナーの明示的な承認が必要。会社の判断では変えない）。

1. **189は「虐待の通告・相談」の番号。** 「叩いてしまいそう」と打ち明けた親本人に案内するなら、「子育ての悩みの相談専用ダイヤル 0120-189-783」を併記すると、通告の番号だと感じて身構える人を減らせるかもしれない（推測）。
2. **親子のための相談LINEは24時間ではなく、地域によっては別の窓口になる。** 深夜に「叩いてしまいそう」と送った人が、案内された LINE で返事を得られない可能性がある（推測）。夜間は189（24時間）を先に出す、などの書き方が考えられる。

## 会社への示唆（3つ以内）

1. **候補1「送信取消で会話を消す」は今の仕組みのまま実装できる。** `@handler.add(UnsendEvent)` で `event.source.user_id` の会話を `sessions.pop(user_id, None)` し、返事はしない（返信用トークンがない）。`user_id` が `None` なら何もしない。テストのダミーに `UnsendEvent` を足す。保存は増えない。
2. **消す経路が増えるので、候補4（返事待ち中に会話が消えたときの KeyError）の優先度を上げる。** 取消は「燃やす」より無意識に起きやすい（推測）ため、同時に直すか、直後に直すのがよい。
3. **SAFETYの相談窓口に「要修正」はない。** ただし「189は虐待対応の番号であること」「親子のための相談LINEは24時間ではないこと」を踏まえ、0120-189-783の併記や夜間の案内順を、オーナー承認が要る**提案**として `docs/owner_todo.md` に載せることを勧める。
