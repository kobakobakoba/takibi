# 調査メモ 2026-11-24：お客さまが焚き火を「ブロック」したとき、焚き火のサーバーの会話はどうなるか ― LINE の unfollow イベントの仕様と、会話を消す小さな改善の材料

調査部。直近の 11-17〜11-23（ローディング表示の SDK、介護者への声かけ、年末年始の統計、Haiku 5.5、窓口の定期確認、ワンオペ育児、返事の長さ）とは重ならないテーマとして、これまで調査・バックログで扱っていない「ブロック（LINE の用語で unfollow）」を選んだ（`Unfollow`・`unfollow`・「ブロックされ」で grep し、10-12 の調査で default ハンドラの対象として一言触れただけと確認）。
社長の方針どおり、SAFETY・PERSONA・外部アカウントには触れない範囲の材料に絞った。相談窓口の確認は 11-28 ごろの予定なので今日はしていない。line-bot-sdk の `reply_message` のタイムアウト（11-17 (b)）も今日はくり返していない。コード・git は触っていない。

## 0. いまの焚き火の動き（`main.py` を読んだ範囲）

- 登録しているイベントは `FollowEvent`（あいさつ）、`UnsendEvent`（送信取消で会話をまるごと消す、270〜276行）、テキストの `MessageEvent` の3つだけ。**ブロック（unfollow）を受ける処理はない。**
- そのため、お客さまが焚き火をブロックしても、焚き火のサーバー（メモリ）の会話は消えない。消えるのは (a) 1時間以上あいたあと、**誰か**が次にメッセージを送って `sweep_idle()`（190〜194行）が走ったとき、(b) プロセスが再起動したとき。また、本人が1時間以内にブロック解除してまた話しかけると、**前の会話の続きとして AI に送られる**（`get_history()` は1時間以内なら同じ会話を返す）。
- つまり「ブロックして終わりにしたつもり」の人の会話が、少なくとも1時間、誰も話しかけない時間帯（夜中など）はそれ以上、メモリに残りうる（コードからの読み。本番で実際にどれくらい残っているかは会社から見えない）。
- `HELP_TEXT` は「1時間以上あくと、次に話しかけたときに新しい会話になり、前の会話は消えます」と書いており、ブロックには触れていない。今の説明は誤りではない。

## 1. LINE の仕様（公式）

### 1-1. ブロックすると unfollow イベントが届く
- LINE Developers の「Receive messages (webhook)」は、unfollow イベントが送られるのは利用者が公式アカウントをブロックしたときで、1対1トークに限ると説明している。[出典A]
- Messaging API リファレンスの unfollow イベントの項目は「ブロックされたとき」のイベントで、項目は `type`・`timestamp`・`source`（利用者のID）・`webhookEventId`・`deliveryContext` など共通のものだけ。**返信用トークン（`replyToken`）は載っていない**（follow イベントには載っている）。つまりブロックされたときは返事を送れず、会話を消すだけになる。[出典B]
- 送信取消（unsend）については、公式が「利用者の意図を尊重し」、後から見たり使ったりできないよう扱うことを勧めている。[出典A] **unfollow について同じような勧め（データを消す等）は公式に見当たらなかった**（出典A、法人向けの開発ガイドライン [出典C] とも）。消すかどうかは事業者の判断。

### 1-2. ブロック解除は follow イベントとして届く
- follow イベントは友だち追加とブロック解除の両方で届き、`follow.isUnblocked` で見分けられる。ただし公式は、この項目で友だち追加とブロック解除を**完全に正確には見分けられない**と注記している。[出典B]
- Python SDK に `isUnblocked`（`FollowDetail.is_unblocked`）が入ったのは 2024-02 のコミット。[出典D] 焚き火は今この項目を使っておらず、今回の改善にも要らない。

### 1-3. 順番・重複
- 再送（初期設定はオフ）があると、受け取る順番が起きた順と違うことがあり、`timestamp` で確かめるよう勧めている。ネットワークの問題などで同じイベントが2回以上届くこともある（`webhookEventId` で見分ける）。[出典A] 第三者の解説も「follow より先に unfollow を処理してしまう」場合に触れている。[出典H]
- 焚き火への当てはめ（推測）：unfollow が遅れて、ブロック解除後の新しい会話の途中に届くと、その新しい会話が消える。失うのは文脈だけで、消える向き（約束1・2の側）なので害は小さい。`timestamp` で比べるには状態を増やすことになるので、比べないほうが今の作りに合う（調査部の見立て）。

### 1-4. ほかにイベントが届かない場面
- 1対1トークで、利用者が**トークルームを削除したとき・LINE のアカウントを削除したとき**に届くイベントは、公式の一覧に見当たらなかった（leave イベントはグループ・複数人トークだけ）。[出典A] これらの場面では、今後も1時間の扱いで消えるのを待つことになる。

### 1-5. ブロック中・解除後の利用者の画面（二次情報）
- 個人どうしのブロックの解説では、ブロックを解除してもトークルームを消していなければトーク履歴はそのまま残り、ブロック中に届いたメッセージはさかのぼって見られない。[出典E] 公式アカウントでも同じかは確かめていない。焚き火の【残るもの】（トーク画面の履歴は端末に残る）とは食い違わない。

## 2. line-bot-sdk（Python, v3）に `UnfollowEvent` があるか

- **一次情報（GitHub の `linebot/v3/webhooks/__init__.py`）は、取得の許可が時間内に下りず読めなかった**（ブロックされた URL：`https://github.com/line/line-bot-sdk-python/blob/master/linebot/v3/webhooks/__init__.py`）。くり返していない。
- 第三者の SDK 解説（tessl.io、3.19.0 のページ）には `class UnfollowEvent(Event)` があり、独自の項目はなく（`reply_token` も持たない）、`source` を受け継ぐと書かれている。[出典F] 第三者の自動生成の要約なので、**判断の根拠にはしない**。
- PyPI の 3.0.3 の説明文には UnfollowEvent の記載はなかった（説明文はイベントの一覧を載せていないので、有無の判断材料にはならない）。[出典G]
- 推測：v3 の webhooks は LINE の OpenAPI 定義から作られており（出典D のコミットでも OpenAPI の定義を更新している）、unfollow は公式リファレンスに載っている古いイベントなので、`>=3.11` のどの版にも入っている見込みが高い。ただし本番の版で import できるかは**未確認**（10-08 の `UnsendEvent` と同じ状態）。

## 3. 作るとしたら（企画部・開発部向けのたたき台。未審査・推測を含む）

- **何をする**：ブロックされたら、その人の会話を `sessions` から消す。`on_unsend()` と同じ形で、`sessions_lock` を取って `sessions.pop(user_id, None)` するだけ。返事はしない（返信用トークンがない）。ログに何も出さない。新しく覚える情報はない。
- **約束との関係**：約束1・2の向き（残す時間を短くする）で、SAFETY・PERSONA・固定文・モデル・`max_tokens`・`requirements.txt`・外部アカウントには触れない。
- **起動を落とさない工夫（推測による提案）**：`UnfollowEvent` が本番の版に無いと、今の冒頭の import（28行）に足した場合は起動時に落ちる。11-16 の `show_loading()` と同じ考え方で、`try: from linebot.v3.webhooks import UnfollowEvent` に失敗したら登録しない形にすれば、無い版でも今の動きのまま（開発部が差分で判断）。
- **テストの注意**：テストのダミー（`tests/test_main.py` 89行）は SDK のクラス名の一覧を持っているので、`UnfollowEvent` を足す必要がある。ダミーのハンドラはクラス名をキーにしており（45〜47行）、`UnfollowEvent` は他と名前がぶつからない。見るとよいこと：(a) 会話がある人がブロックすると会話が消える、(b) 他の人の会話は消えない、(c) 会話がない人のブロックでも落ちない、(d) 返信を呼ばない、(e) `source` に `user_id` がないイベントでも落ちない（`on_unsend` と同じ `getattr`）。差分の見込みは `main.py` 10行前後＋テスト30行前後（推測）。
- **安全審査部に見てほしい点**：ブロック→1時間以内に解除→また話す、の場合に `s["safety"]`（危ない言葉が当たったフラグ）も一緒に消え、次の燃やすで応援リンクが出うる。ただしこれは今でも「燃やす」「送信取消」「1時間」で同じことが起きるので、新しい穴ではない見込み（推測）。ブロック中は焚き火から何も届けられないので、消しても安全の案内が減ることはない。
- **しないこと**：`HELP_TEXT` に「ブロックすると消えます」と足すのは別の判断（イベントが必ず届くとは言えない。1-3）。今回は「黙って早く消す」だけにとどめるのが小さい。

## 会社への示唆

1. **企画部へ（コードの候補あり）**：「ブロックされたら会話を消す」は、待ちの条件がなく、SAFETY・PERSONA・外部アカウントに触れず、約束1・2をより確かにする小さな改善の候補になりうる（上の 3）。ただし `UnfollowEvent` の有無が本番の版で未確認なので、import が失敗しても起動を落とさない形にすることを条件にするのがよい（推測による提案）。安全審査部の確認点は 3 の最後のとおり。作らない判断もありうる（1時間で消える今の作りで大きな害は見えていない）。
2. **企画部へ（説明文）**：`HELP_TEXT` は今のままで誤りはない。作った日に【消えるもの】へ「ブロックしたとき」を足すかは、イベントの届き方が保証されないので別の日に判断する（足すなら「必ず」「すぐ」と書かない）。12月上旬の説明文の定期見直しで一緒に見てもよい。
3. **広報部へ**：「ブロックすれば消えます」「やめたくなったらブロックで全部消えます」とは書かない（今は消えない。作ったあとも届かない場合がありうる）。消し方として案内するのは引き続き「燃やす」だけにする。
