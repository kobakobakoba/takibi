# 調査メモ 2026-10-09：LINE の Webhook 再送と reply token の仕様／返信が失敗したとき何が起きるか

調査部。テーマは企画部の依頼（バックログ候補「LINE への返信が失敗したときの扱い」）。
(1) ボットのサーバーが 2xx 以外を返したときの Webhook 再送の仕様（初期設定、見分け方、reply token の扱い）。
(2) `main.py` の `reply()` が try で囲まれておらず例外が `/callback` まで上がる件を、握りつぶしてよいかの判断材料。
(3) 副テーマ：スタンプなど文字以外のメッセージを受けるのに line-bot-sdk v3 で何の import が要るか。

※ 今日読めたのは LINE Developers の「Webhookを受信する」（日本語・英語）、「Webhookのエラーの原因と統計情報を確認する」（日本語）、Messaging API リファレンスの nojs 版（日本語・英語）。**GitHub（SDK のソース・サンプル）、PyPI、Flask の公式ドキュメント、LINE の「メッセージを送信する」ページは、取得の許可待ちが切れて読めなかった。**

## 1. 確認できたこと（公式ドキュメント）

### 1-1. Webhook の再送（redelivery）

| 項目 | 内容 | 出典 |

| 回数・間隔 | **非公開**。予告なく変わることがある | 同上 |

### 1-2. Webhook のエラーの扱い（タイムアウト）

- LINE は Webhook のエラーの原因を4つに分けている：`could_not_connect`、`request_timeout`、`error_status_code`、`unclassified`。
- `request_timeout` は、ボットのサーバーが「2秒以内にレスポンスを返さなかった」場合。
- エラーの統計情報の表示は初期設定でオフ。コンソールの［Messaging API設定］で［エラーの統計情報］をオンにすると見られる。

出典：LINE「Webhookのエラーの原因と統計情報を確認する」（日本語）

### 1-3. reply token（応答トークン）

| 項目 | 内容 | 出典 |
| --- | --- | --- |
| 有効期限 | Webhook を受け取ってから**1分以内**に使う。1分を過ぎた場合の動作は保証されない。この期限は予告なく変わることがあるので、頼りきらないようにとの注意あり | Messaging API リファレンス（英語） |
| 使える回数 | **1回だけ**（"Reply tokens can only be used once."） | 同上 |
| 再送されたイベントの reply token | 再送を受け取ってから1分以内なら使える。ただし、**元の reply token がすでに使われていた場合**、または**イベント発生から20分たった場合**は使えない | 同上 |
| 使えない token で返信したとき | エラーメッセージ `Invalid reply token`（期限切れ・使用済みが原因として挙げられている）。返信 API の説明では、`400` は無効な reply token またはメッセージオブジェクトを指定したときと書かれている | リファレンス（日本語・英語） |
| 1回の返信で送れる件数 | 最大5件 | リファレンス（英語） |
| 共通のステータスコード | 400、401、403、409（同じリトライキーのリクエストを受付済み）、410、413（2MB超）、429（レート超過）、500 など | リファレンス（英語） |
| standby のとき | チャネルが `standby` のときは reply token が含まれない | リファレンス（日本語） |

## 2. 焚き火のコードに当てはめると（コードを読んでの整理。本番の様子は会社から見えない）

`main.py` を読んで確認したこと：

- `/callback` は `handler.handle()` を呼び、`InvalidSignatureError` だけを受けて 400 を返す。ほかの例外は受けていない。
- `on_message` では、Claude API の呼び出し（と空の返事）だけが try の中。`reply()` は、普通の返事・おわび・「燃やす」・「使い方」・あいさつ（FollowEvent）のどれでも try の外にある。
- 普通の返事では、**履歴に AI の返事を足してから** `reply()` を呼ぶ。
- Claude の呼び出しは Webhook のリクエストの中で同期的に行われ、終わるまで `/callback` は応答を返さない。
- `README.md` の本番手順では「Webhookの利用」をオンにするとだけ書かれている。**本番で［Webhookの再送］がオンかオフかは会社からは分からない（未確認）。**

### 2-1. `reply()` が例外を出したとき（推測を含む）

1. 例外は `handler.handle()` を通って `/callback` まで上がり、Flask が 500 を返す（**推測**。Flask の一般的な動きで、今日は Flask の公式ドキュメントを読めなかった。line-bot-sdk の `handle()` が例外を受け止めないことも、ソースを読めず未確認）。
2. **再送がオフ（初期設定）なら**：LINE は送り直さない（1-1 の条件から）。利用者には何も届かず、それで終わる。履歴には利用者が見ていない AI の返事が残る（コードから）。
3. **再送がオンなら**：同じイベント（同じ reply token）がもう一度届く可能性がある（回数・間隔は非公開）。そのとき `on_message` がもう一度動き、**同じ発言が履歴にもう1つ入り、Claude をもう一度呼ぶ（料金も2回分）**（コードからの推測）。返信できるかは、元の token が使われたかどうかで決まる（1-3）。
   - 失敗の原因が「token 使用済み・期限切れ」なら、再送でも返信できず、また失敗する（1-3 から）。
   - LINE 側の一時的なエラーで token が使われていなければ、再送で返信が届くこともある（推測）。

### 2-2. いちばん気になる点：2秒のタイムアウト（推測）

- Claude の返事を待つ時間は、多くの場合2秒を超える（**推測**。本番の応答時間は会社から見えない）。そうなら、LINE から見ると普通の会話の多くが `request_timeout`（エラー）になっている可能性がある。
- 公式の再送条件は「2xx を返さなかった」で、タイムアウトが再送の対象になるかは明記されていない（**未確認**）。もし対象になるなら、**再送をオンにすると、普通に返事ができた会話でも同じイベントが届き直し、Claude を二重に呼んだり、使用済みの token で返信して失敗したりする**おそれがある（推測）。
- 公式は「長期間受信に失敗していると Webhook の送信を止める可能性がある」とも書いている。タイムアウトがこれに数えられるかは未確認だが、焚き火が今も返事できているなら（会社からは見えない）、少なくとも止められてはいない（推測）。
- 公式の推奨は「非同期で処理する」。つまり、すぐ 200 を返してから裏で Claude を呼び、reply token の1分以内に返信する形（推測を含む設計の読み）。ただし焚き火は会話をメモリで持ち、ワーカー1・スレッド4で動くので、作り替えるなら別の大きな変更になる。

### 2-3. 握りつぶしてよいかの材料（推測を含む）

- **再送がオフのとき**：`reply()` の例外を握りつぶして 200 を返しても、利用者から見た結果（何も届かない）は今と同じ。違いは LINE への応答が 500 から 200 になることと、サーバーのエラー表示が減ることだけ（推測）。二重返信の心配は再送の仕組みからは生じない。
- **再送がオンのとき**：握りつぶして 200 を返すと再送されなくなる。reply token は1回しか使えず、再送されても元の token が使われていたら返信できないので、失った返信を再送で取り戻せる場面は限られる（1-3 から）。一方で、再送されると Claude の二重呼び出しと履歴の重複が起きうる（2-1）。**握りつぶしの方が害が少ない可能性が高い**（推測）。
- どちらでも、**ネットワークの問題による重複は再送の設定と関係なく起こりうる**（1-1）。重複を完全に防ぐには `webhookEventId` を覚えておく必要があり、会話内容ではないが「何かを記録する」ことになる。今は対策しなくても、起きたときの害は返事が1つ増える・Claude を1回余分に呼ぶ程度（推測）。
- 注意：握りつぶすときは、例外の中身（LINE の応答本文など）を `print`／`logging` に出さない方針（会社のルール）に合わせる。今は未処理の例外として、Flask／gunicorn がエラーの詳細をログに出している可能性がある（推測。ログは会社から見えない。LINE のエラー本文に利用者の発言が含まれるかは未確認）。

## 焚き火への示唆（3つ以内）

1. **`reply()` の失敗は握りつぶしてよい、という判断材料がそろった（推測を含む）。** 再送は初期設定でオフで、reply token は1回きり・1分以内・再送でも使用済みなら使えない。返信の失敗を再送で取り戻せる場面は少なく、オンにしていると Claude の二重呼び出しや履歴の重複のほうが起きやすい。全部の `reply()` 呼び出しを try で囲み、例外の中身は出力しない形が小さくて安全（LINE SDK に新しく依存しない）。あわせて、返信に失敗したときは、足したばかりの AI の返事を履歴から外すかも企画部で検討してほしい。
2. **オーナーに［Webhookの再送］がオフかを確かめてもらう（`docs/owner_todo.md` 候補）。** 焚き火は Claude を待ってから応答するため、LINE から見ると2秒のタイムアウトになっている会話が多い可能性がある（推測）。再送がオンだと二重処理のおそれがあるので、オフのままにしてもらうのが安全。「エラーの統計情報」をオンにすれば、タイムアウトの多さをオーナーが見られる（会話の内容は出ない仕組みだと思われるが、統計の中身は今日は詳しく確認していない）。
3. **スタンプ対応の import は今日も未確認。** `StickerMessageContent` を足すか、`MessageEvent` だけで受けるかは SDK のソースを読めた日に決める。それまでは `UnsendEvent` の起動確認待ちの方針どおり、SDK への新しい依存は重ねない。
