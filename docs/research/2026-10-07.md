## 2. gunicorn のスレッドワーカーで dict を共有するときの注意

`README.md` の本番の起動コマンドは `gunicorn main:app --workers 1 --threads 4`。`main.py` は全員の会話をモジュール変数の `sessions: dict` に持っている。

### 2-1. この起動コマンドは、1つのプロセスの中で4つのスレッドが動く（確認済み）

- gunicorn の設定ドキュメント（20.x版）：既定の sync ワーカーで `threads` を2以上にすると、自動で **gthread ワーカー** に切り替わる、と書かれている。
- gunicorn の設計ドキュメント（21.0.1版）：gthread は、受け付けた接続をスレッドプールに渡して処理する方式。
- つまり、**同じプロセス内の最大4スレッドが同じ `sessions` を同時に読み書きしうる**（ワーカーが1つなので、プロセスをまたいだ食い違いは起きない）。
- gunicorn のドキュメントには、アプリ側のスレッドセーフについての注意書きは見当たらなかった。守るのはアプリ側の責任。

### 2-2. 反復中に dict が変わると RuntimeError になりうる（確認済み）

- Python の公式ドキュメント（標準型、`Doc/library/stdtypes.rst`）：dict のビュー（`items()` など）を回している間に要素を追加・削除すると、**`RuntimeError` になるか、全要素を回りきれないことがある**、と明記されている。
- 公式チュートリアル（制御構文の章）：回している最中にその入れ物を変える処理は間違えやすいので、**コピーを回すか、新しい入れ物を作る**のが素直だ、と例付きで勧めている（例は `users.copy().items()` を回しながら `del users[user]`）。
- スレッドが関係する場合（推測を含む）：CPython の通常版では GIL により一度に1スレッドしか Python コードを実行しないが、スレッドの切り替えは for 文の途中でも起きうる。そのため、あるスレッドが `for ... in sessions.items():` で回している途中に、別スレッドが `sessions.pop(...)` や `sessions[新しい人] = ...` をすると、上の `RuntimeError` に当たりうる。候補1（全員分の古い会話を消す）はまさにこの形なので、**コピーを回すか、ロックで守る**必要がある。

### 2-3. 単発の操作と「確認してから操作」の違い（確認済み。ただし出典は free-threaded 版向け）

- 公式の「Thread Safety Guarantees」ページは、**GIL を外した free-threaded 版**の保証を説明するページで、GIL ありの通常版では多くの操作が暗黙に1つずつ実行されると書かれている。本番が通常版か free-threaded 版かは会社からは見えない（Render の Python 設定次第。普通は通常版と考えるが未確認）。
- 同ページによると、`d.get(key)`、`d[key] = v`、`d.pop(key)` などの**単発の操作は安全**。一方、**反復は決して一体の操作にならない**ので、他スレッドが変えうる dict はコピーを回すよう勧めている（例：`d.copy().items()`）。
- また、`if key in d: del d[key]` のような**「確認してから操作」は一体ではない**（確認と操作の間に他スレッドが割り込める）。代わりに `d.pop(key, None)` を使うか、例外で受けるよう勧めている。共有する場合は外側での同期（ロック）を検討するように、とも書かれている。
- 今の `main.py` の消す処理は `sessions.pop(user_id, None)` なので、この点では推奨どおり。一方、`get_history` の「`sessions.get` → なければ新しく作って入れる」や、`on_message` の「履歴に足す → `updated` を書く」は複数の操作の組み合わせで、ロックがなければ一体にはならない（コードを読んでの指摘）。

### 2-4. threading.Lock の使い方（確認済み：`docs.python.org/3/_sources/library/threading.rst.txt`）

- `Lock` は「ロック中／解除」の2状態。`acquire()` は解除なら取ってすぐ戻り、ロック中なら他スレッドが `release()` するまで待つ。解除状態のロックを `release()` すると `RuntimeError`。
- **`with lock:` で書くのが基本。** ブロックに入るときに `acquire`、出るとき（例外でも）に `release` が呼ばれる。`acquire()` → `try` → `finally: release()` と同じ意味。
- `Lock` は同じスレッドが2回取ろうとすると**自分で詰まる**（再入できない）。入れ子で取る可能性があるなら `RLock` を使う。
- CPython では GIL のため一度に1スレッドしか Python コードを実行しないが、I/O 待ちが多い処理には threading が今も適している、と書かれている。Python 3.13 以降は GIL を外した実験的なビルドもある（既定ではない）。

### 2-5. 焚き火に当てはめると（推測。実装判断は企画部・開発部）

- **ロックの中で Claude API を呼ばない。** API 呼び出しは数秒かかるので、その間ロックを持つと4スレッドが実質1本になり、他の人の返事が遅れる（推測）。ロックは `sessions` を読む・書く短い区間だけに使う。
- 候補1（古い会話の一括削除）は、`with lock:` の中で `list(sessions.items())` などのコピーを作って回し、`sessions.pop(uid, None)` で消す形が、公式の勧め（コピーを回す、pop を使う）に合う。
- `Lock` を使うなら、ロックを取った関数の中から、同じロックを取る別の関数を呼ばない設計にする（`Lock` は再入できないため）。迷うなら `RLock`。
- テストでは、ロックがあっても今の「返事待ち中に消えても落ちない」テスト（偽 Claude の途中で `sessions.pop`）がそのまま通ることを確かめるとよい。偽 Claude の途中処理がロックを取りに行く形にすると、ロックの持ち方によっては詰まる（デッドロック）ので注意（推測）。

## 3. 競合が「保存しない／消せる」をどう説明しているか

LINE上の「愚痴聞き専用」で、データの扱いを詳しく書いているサービスは今日は見つけられなかった。参考になった2例。

| サービス | 種類 | 「保存・削除」の説明 | 気づいたこと |
| --- | --- | --- | --- |
| LINE AIフレンズ（LINEヤフー、2025年8月開始と報道） | LINEアプリ内のAIキャラクターとのトーク | 解説記事によると、会社はトーク内容を第三者に開示しないと説明。キャラクターを削除（またはブロック）すると、関係性とトーク履歴が消えて**復元できない**。トークはLINEのトーク一覧に並ぶので、画面をのぞかれると見られる、という注意も記事にある | 「消すと戻らない」を**利用者の操作**として説明している。サーバー側に何が残るかは記事からは分からない。課金は1通ごとにポイントやLINEコインを使う方式 |
| AIセラピスト（個人開発のiPhoneアプリ） | 単独アプリ（LINEではない） | 説明文に**「会話の情報はサーバー上には保存されません」**とある | 一方で App Store のプライバシー表示には、位置情報・デバイスIDなどを第三者広告の目的で集めうる、とある。無料・広告あり。「会話は保存しない」と「広告のためのデータ収集」が同居している |

※ どちらも記事・ストアページの記載を確認したもので、実際にサーバーに何が残るかは確認できない。個人の投稿は扱っていない。

### 焚き火との比較（推測を含む）

- 焚き火は「燃やす」と送信取消で消え、広告を出さない（約束3）。競合は「消せる」を言っていても、**どこから消えるのか**（画面か、サーバーか）を書いていない例があった。焚き火の `HELP_TEXT` は「焚き火のサーバーから消える／LINEのトーク画面には残る」と分けて書いており、ここは差別化になる（推測）。
- 「保存しない」と書きつつ広告用のデータを集める例がある。焚き火は広告なしなので、紹介文では「愚痴の内容を広告に使わない」だけでなく「広告そのものを出さない」と言える（広報部向け）。ただし言い過ぎ（「完全に消える」など）は2026-10-05 の申し送りどおり避ける。

## 会社への示唆（3つ以内）

1. **候補1と候補2は一緒に、`threading.Lock` 1つで小さく実装できる。** 本番は gthread で4スレッドが同じ `sessions` を触るため、全員分を回す一括削除は、ロックの中でコピー（`list(sessions.items())` など）を回し `pop(uid, None)` で消す。ロックは `sessions` の読み書きの短い区間だけに使い、**Claude API の呼び出し中は持たない**。`Lock` は再入できないので、ロックを取る関数同士を入れ子にしない。
2. **「まもろうよ こころ」は有効で「要修正」なし。** ただしサイト内に24時間の窓口（#いのちSOS、よりそいホットライン、あなたのいばしょ）があるので、深夜の利用者向けに「24時間の窓口名を1つ併記する」案を、前回の189の提案と合わせてオーナー承認待ちの提案に加えることを勧める（番号は変わりうるので書くなら窓口名まで、が保守しやすい）。
3. **競合は「消せる」の範囲（画面かサーバーか）をあいまいにしがち。** 焚き火の `HELP_TEXT` の「サーバーから消える／トーク画面には残る」という書き分けと「広告を出さない」は、そのまま広報の強みになる。候補3の文言見直しでも、この書き分けを崩さないこと。
